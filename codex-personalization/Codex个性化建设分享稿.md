# 我如何把 Codex 逐步搭成个人工作系统

整理日期：2026-10-27。本文分享建设方法与当前结构，不包含个人凭据、业务知识库或可直接套用的账号权限。

## 1. 为什么要做这件事

一开始，Codex 是每次重新说明背景的助手。使用一段时间以后，真正影响效率的变成了几个重复问题：它是否理解我的表达习惯，能否沿用已确认的方法，是否知道资料在哪里，能不能稳定生成我要的成果，以及换一台电脑后这些积累还在不在。

我的建设思路，是把日常对话里有价值的内容逐步分成五类：协作规则、长期知识、可复用技能、外部工具连接、重复性检查。每类放在合适的位置，形成可以解释、可以备份、可以迁移的工作系统。

## 2. 已经形成的结构

| 层次 | 解决什么问题 | 我的建设内容 | 换机恢复方式 |
|---|---|---|---|
| 协作规则 | 每次都要重新交代怎么配合 | 项目 AGENTS.md、中文表达偏好、工作与验收规则 | 恢复指令文件，保持原作用域 |
| 知识与记忆 | 换会话、换项目后丢失背景 | Obsidian 纯 Markdown 知识库、偏好、SOP、决策、知识卡 | 取回私有知识库与本地快照 |
| 可复用技能 | 相同工作反复从头描述 | 17 个个人技能目录，保留参考资料与脚本 | 迁移技能目录并补依赖 |
| 官方与平台能力 | 文档、浏览器和设计工具缺少执行能力 | 当前配置启用 14 个插件 | 新设备重新安装和授权 |
| 外部知识连接 | 资料在本地或远程平台，模型拿不到 | Obsidian MCP、腾讯文档 MCP；保留 RAGFlow MCP 代码 | 重新定位程序、配置环境变量、验证连接 |
| 持续维护 | 知识库时间久了失去维护 | 每日知识健康检查、每日私有 GitHub 推送 | 重建任务，验证一次后启用 |
| 个人体验 | 长期工作时缺少熟悉感 | 中文界面、技能快捷键、自定义 v2 桌宠 | 恢复资源与选项 |

“文件存在”“配置启用”“实际能运行”是三种状态。下面记录的数量来自旧设备当前清单，不代表全部能力已经在新设备验证。

## 3. 先固化协作方式

我希望 Codex 更像一个长期合作的项目搭档：默认中文，先说结论；信息不足时先判断，再补关键问题；先看已有材料，沿用已确认术语；修改重要文件前备份；完成后说明改了什么、怎么验证、还有什么没验证。

这些要求写进项目级 `AGENTS.md` 和知识库的个人偏好笔记。它们也规定了更具体的行为：会议纪要不能编造责任人和期限，业务分析要区分事实、判断与待确认项，原始材料不能直接变成对外承诺。

这里有一个换机容易遗漏的细节：旧设备的全局 `AGENTS.md` 是空的，实际规则主要在项目目录。只复制软件配置，并不能恢复这些协作方式。

## 4. 让知识积累成为可维护的文件

我把长期知识放在 Obsidian，内容以 Markdown、YAML 属性和双链表达。

```text
知识库/
├─ 00-Codex永久记忆/       启动说明、偏好、SOP、跨项目决策
├─ 01-Projects 项目/       各项目的知识和结论
└─ 10-自生长知识系统/      概念、方法、问题和复盘
```

Office、音视频、压缩包和运行时留在源项目。知识库保存提炼后的结论、来源、日期和适用范围。这样换一个 Agent 或编辑工具，知识仍是普通文件，不依赖某个会话才能解释。

知识增长也需要明确的写入规则：日常检查只扫描变化，不自动提炼、不自动写入永久记忆；需要沉淀时由我明确提出。查知识和改知识分别管理，避免每天自动生成一批无法追溯的“记忆”。

Codex 自身的记忆摘要也作为辅助参考保存，但它与 Obsidian 长期知识库不是同一种东西。迁移时，自动生成的摘要应当复核，不能把旧机器路径与旧会话标识原样当成新环境事实。

## 5. 把高频工作做成技能

目前个人技能覆盖六组工作：

| 方向 | 已建设或安装的技能 | 价值 |
|---|---|---|
| 业务问数与产品知识 | BI 数字员工、SAP Emarsys 考试辅助 | 复用指标口径、字段、规则和培训资料 |
| 录音与会议 | 音频转写 | 形成带时间戳的 Markdown、SRT、JSON |
| 知识管理 | Obsidian Markdown、CLI、Bases、JSON Canvas、RAGFlow 运维 | 管理知识结构和检索流程 |
| 页面与关系图 | 前端设计、设计品味、UI/UX、关系架构图 | 提高页面与图解的可用性与表达质量 |
| 项目与验证 | 项目执行框架、需求梳理、Playwright、PDF | 让计划、脚本、成果和验证可追溯 |
| 个性化资源 | v2 桌宠制作 | 生成、修复和校验自己的桌宠资源 |

一个技能除了 `SKILL.md`，往往还有参考资料、脚本、示例和数据文件。迁移时要保留完整支持文件。例如 BI 技能包括字典、全局变量、SQL 模板和测试案例；只复制入口说明会丢失真正的业务能力。

技能也可能依赖 Python 包、浏览器、模型文件或特定宿主工具。文件搬过去以后，还要区分“可直接使用”“需要补依赖”“需要重新连接宿主”三种情况。

## 6. 把执行能力与知识分开

插件负责提供文档、电子表格、演示文稿、PDF、浏览器、桌面控制、Figma、GitHub、视频和可视化等能力。它们有些由应用托管，有些需要外部账号。

因此，迁移策略是保留插件清单，在新设备重新安装；登录和权限重新验证。旧设备缓存中的插件代码、运行时哈希路径、浏览器管道和信任指纹，适合作为诊断线索，不适合作为通用安装包。

模型配置同样需要区分。旧设备记录了模型、服务商、协议和推理偏好，但新设备能否使用某个模型取决于实际账号与服务商。历史模型名称不能代替新环境的可用性检查。

## 7. 接入本地与远程知识

本地 Obsidian MCP 提供读取和检索 Markdown 的能力，并限制路径访问范围。它依赖知识库文件和本地服务程序；换机时主要调整可执行程序与工作区路径。

腾讯文档通过远程 MCP 接入，认证信息引用环境变量。迁移时只保留服务定义和变量名称，凭据在新设备重新设置。

RAGFlow 也建设过本地 REST API 到 MCP 的封装，代码仍可恢复。但当前配置里没有启用它，因此整理为“已有成果、待重新接入”，而不是宣称当前在线。

这些连接说明了一个关键区别：复制一个说明文件不会自动赋予系统访问权限。每个外部系统仍需要相应账号、凭据和真实调用验证。

## 8. 用自动化维护知识

我把维护拆成两个任务：每日检查知识库结构和项目变化；每日把私有知识库提交到 GitHub。检查不产生新知识，备份也不会自动把内容发布到公开仓库。

迁移时要保留任务意图、提示词、时间与状态，然后在新环境重建。旧设备的任务身份、会话绑定和运行缓存，不应直接复制后假定已经生效。

对于已经暂停的任务，恢复后继续保持暂停。对于计划任务，还要检查执行日志、Git 状态与远端提交；单看任务管理器显示成功不足以证明同步完成。

## 9. 保留个人体验

我还保留了中文界面、上下文用量显示、模型选择视图、技能快捷键和自定义桌宠。这些内容不决定业务能力，但会影响长期使用的熟悉感。

桌宠的可迁移资产是定义文件和精灵图，而不是旧版本应用的内部缓存。快捷键也需要在新版本中验证是否与常用操作冲突。

## 10. 换机时真正需要保存什么

| 资产 | 保存方法 |
|---|---|
| 协作规则与偏好 | 指令文件、偏好笔记、SOP |
| 个人技能 | 完整技能目录及其支持文件 |
| 长期知识 | 私有 Git 仓库与离线 Markdown 快照 |
| MCP 实现 | 服务代码、无凭据配置、环境变量名称 |
| 自动化 | 任务定义和恢复说明 |
| 插件 | 安装清单、依赖、重新授权步骤 |
| 界面与桌宠 | 选项清单、自定义资源 |
| 账号与凭据 | 新设备重新登录或从自己的凭据管理方式恢复 |

我会随换机包提供一段给新 Codex 的初始化提示词，让它先检查清单，再逐步恢复，最后按验收表确认。这样不需要再次从聊天中一点点回忆曾经做过什么。

## 11. 本次整理的边界

这份分享基于截至 2026-10-27 能在当前设备核验的配置、文件和任务。它不承诺找回已经删除且没有记录的历史建设，也不等于新设备恢复实测。

个人换机包包含业务参考资料与知识，只适合本人保存。对外分享时使用本文，不直接分享个人包。

官方参考：[配置](https://developers.openai.com/codex/config-basic/)、[技能](https://developers.openai.com/codex/skills/)、[MCP](https://developers.openai.com/codex/mcp/)、[自动化](https://developers.openai.com/codex/app/automations/)。官方技能路径说明与旧设备实际加载目录存在差异，新设备应按其版本检查技能是否被发现。
