# 真实场景验证记录

> 用途：记录用户提供的真实业务问法，验证当前知识库是否能够完成“问题识别 -> 反问判断 -> 指标/口径映射 -> SQL 模板选择”的链路。

## RS001

| 项目 | 内容 |
|---|---|
| 原始问题 | 帮我看一下5月份购买人数的新老客占比以及新客中的会员占比 |
| 验证时间 | 2026-06-09 |
| 识别指标 | 购买人数、新客购买人数、老客购买人数、新客占比、老客占比、新客中的会员占比 |
| 默认时间理解 | 如无补充，按当前年份理解为 2026-05-01 00:00:00 至 2026-06-01 00:00:00，时间字段默认 `order_start_time` |
| 默认订单口径 | 有效订单 |
| 预期动作 | `ask_clarification` |
| 全局变量处理 | 需要先让提需人重设/确认本次查询的全局变量包，再进入 SQL 生成。 |
| 阻断原因 | 缺少 `shop_id`；未确认订单状态、订单类型、时间字段是否沿用默认值；“新客/老客”口径未指定；会员限制口径未确认。 |
| 建议反问 | 为了重设本次查询的全局变量，请确认：1）`shop_id` 或店铺范围；2）订单状态是否使用默认“有效订单”；3）时间是否按默认“下单时间”；4）订单类型是否按默认不额外过滤；5）新客/老客口径选择历史、365、180 还是自定义天数；6）新客中的会员占比是否限制“先开卡后下单”。 |
| 可用 SQL 模板 | 新客：`sql.order.historical_new_customer_metrics` 或 `sql.order.rolling_new_customer_metrics`；老客：`sql.order.old_customer_by_difference`；会员关联：需在新客人群基础上关联 `dwm.member_info_d`，默认通过 `shop_id + cjyx_encrypt_pin` 匹配 |
| 验证结论 | 当前初始判断不完整：该题不应只反问零散参数，而应先触发“全局变量重设/确认”，再补充新老客和会员口径。 |

### RS001 二次确认后的 SQL 生成

| 项目 | 内容 |
|---|---|
| 用户补充 | `shop_id=小寒test`；订单状态取完成；时间使用支付时间；过滤购物金订单，`sku_id='test购物金'`；历史新老客；`brand_id=A`；不需要设置先开卡后下单 |
| 用户修正 | 订单表关联会员表时，一般通过 `shop_id + cjyx_encrypt_pin` 双字段匹配，不默认使用 `brand_id`。 |
| 全局变量记忆 | 本轮确认值写入 `brand_id=A + 渠道=京东` 的会话记忆；后续同键提问时可带出这些默认值，请提需人确认是否沿用。 |
| 最终动作 | `generate_sql` |
| 时间范围 | 按当前项目日期理解为 2026 年 5 月：`2026-05-01 00:00:00` 至 `2026-06-01 00:00:00`，左闭右开 |
| SQL 目标 | 输出 5 月购买人数、新客购买人数、老客购买人数、新客占比、老客占比、新客中的会员人数、新客中的会员占比 |
| 验证结论 | 全局变量重设完成后，可以生成组合型占比 SQL；该场景后续适合沉淀为组合 SQL 模板。 |
