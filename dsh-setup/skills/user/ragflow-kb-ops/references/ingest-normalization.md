# 源数据规范化与入库规范

目标：让 RAGFlow 解析出的切片**结构完整、标题可用、命名本身就能被检索命中**。

## 1. 格式转换决策

RAGFlow 对办公文档的解析质量差异很大，入库前先统一格式：

| 源格式 | 建议 | 原因 |
|---|---|---|
| `.pptx` | 转 PDF 后入库 | 一页幻灯片会被切成一个片段，页内标题与正文关系保留；直接入库常出现标题与正文错位、备注丢失 |
| `.xlsx` | 转 Markdown 后入库 | 表格天然适合 Markdown；直接入库容易丢表头、合并单元格错乱 |
| `.docx` | 保留原格式 | 解析器对 Word 支持较完善 |
| `.pdf`（文本型） | 保留 | — |
| `.pdf`（扫描/图片型） | 需要 OCR | 纯文本抽取会得到空白；确认解析器已启用 OCR 再入库 |
| 图片 / 截图 | 谨慎 | 单张图片的信息密度低，通常更适合回填进文档 |

转换脚本要能**批量 + 可重跑**：按扩展名筛选、输出到独立目录、同名冲突加后缀，
并打印"转换 N 个，跳过 M 个"的汇总，便于复跑时确认幂等。

Windows 上用 Office COM 把 pptx 另存为 PDF（`SaveAs($dst, 32)`）比第三方转换器更稳，
但需要本机装有 PowerPoint，且必须显式关闭文档、释放进程——批量转换时超时/僵尸进程是常见故障点。

## 2. 命名规范

命名是**检索信号**，不只是给人看的。先定规则再批量改，改完再上传，避免同库内新旧规则混用。

推荐的通用骨架（按业务调整字段顺序，保持全库一致）：

```text
【文档类型】品牌或对象-文档主题-版本或日期
```

落地要点：

- **文档类型**用方括号统一包裹，便于一眼分类和按前缀筛选（如 `【产品介绍】【报价】【案例】【SOP】`）。
- **品牌/对象**放在类型之后，保证同类文档聚在一起。
- **版本与日期**放在最后；同一文档多版本时，让最新版能被一眼识别。
- 特殊场景可以整体替换命名规则，但要在库里保持一致——**混用比"不够好"的规则更糟**，
  因为它让检索结果无法预期。
- 重命名只动文件名，不要动内容；重命名后如果文件已入库，需要重新上传（旧文档要做删除或标记失效）。

## 3. 幂等入库

批量同步时**永远先查再传**：

1. 拉取目标数据集现有文档清单（按文件名建集合）。
2. 遍历本地文件，命中同名的**跳过**，只上传新增与明确需要替换的。
3. 上传后触发解析，轮询 `progress` 到 1（或 `run` 状态为完成）再进入下一步。
4. 汇报时给三类计数：新增 / 跳过 / 失败，便于核对。

替换已有文档时，注意"上传同名文件"不一定会覆盖旧记录——确认实例行为，必要时先删旧文档。

## 4. 元数据字段

文档级元数据可在**不重解析**的前提下补齐（走 `metadata/update` 接口），是性价比最高的一步。
推荐字段（按业务裁剪）：

| 字段 | 用途 |
|---|---|
| 文档类型 | 与命名中的类型一致，便于过滤 |
| 品牌 / 客户 | 按客户隔离检索 |
| 产品线 | 细粒度过滤 |
| 是否可外发 | 合规控制；批量导入时先给默认值再逐步确认，不要默认"可外发" |
| 生效时间 / 失效时间 | 处理新旧口径冲突 |
| 是否有效 | 软失效标记，避免删文档丢信息 |

批量补元数据时按文档类型给不同默认值，比逐条人工填快得多；真正需要人判断的字段（如是否可外发）
单独列出清单交业务确认。

## 5. 重解析的代价

切分策略、解析器或数据集级索引配置变更后，**已入库文档需要重解析才会生效**，代价是：

- 文档 id 会变（后续引用要重新对应）
- 全库重解析 + 重建索引通常是小时级
- RAPTOR / GraphRAG 需要重跑，且这段时间内检索结果处于"半新半旧"状态

所以：**先在小数据集上验证切片策略，确认后再对全量执行**，不要在线上主库直接试。
